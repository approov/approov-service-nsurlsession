# Approov Service for NSURLSession 

A wrapper for the [Approov SDK](https://github.com/approov/approov-ios-sdk) to enable easy integration when using [`NSURLSession`](https://developer.apple.com/documentation/foundation/nsurlsession) for making the API calls that you wish to protect with Approov. In order to use this you will need a trial or paid [Approov](https://www.approov.io) account.

See the [Quickstart](https://github.com/approov/quickstart-ios-objectivec-nsurlsession) for usage instructions.

The Approov Service for `NSURLSession` wraps the Approov iOS SDK and provides an `ApproovNSURLSession` class that mirrors the familiar `NSURLSession` interface. When your app makes requests through `ApproovNSURLSession`, the service layer can automatically:

* fetch an Approov token for configured API domains;
* add the token to the outgoing request;
* apply Approov-managed dynamic certificate pinning;
* substitute protected secrets into request headers or query parameters at runtime.

Use this package if your iOS app is written in Objective-C, or has Objective-C networking code, and you make API calls using `NSURLSession`.

For Swift apps using `URLSession`, use the Swift [Approov Service for URLSession](https://github.com/approov/approov-service-urlsession) instead.

## How the service layer works

The integration has four parts:

1. Add the Approov service dependency to your app.
2. Initialize `ApproovService` once, before making protected network requests.
3. Create your sessions using `ApproovNSURLSession` instead of `NSURLSession`.
4. Configure your API domains in Approov so the service layer knows which requests should receive Approov protection.

The service layer does not modify every network request made by your app. It only protects requests made through `ApproovNSURLSession`.

For API domains configured for Approov token protection, the service layer adds an `Approov-Token` header by default. Your backend API must then verify this token before allowing access.

For secrets protection, the service layer can replace placeholder values in headers or query parameters with secure values delivered by Approov only to apps that pass attestation.

## Requirements

To use this service layer you need:

* an iOS app using `NSURLSession`;
* iOS 12 or later;
* CocoaPods;
* a trial or paid Approov account;
* the Approov configuration string from your onboarding email or Approov CLI;
* backend token verification if you are using API protection.

## Add the dependency

Add the service layer to your app's `Podfile`:

```ruby
target 'YourApplication' do
    use_frameworks!
    platform :ios, '12.0'
    pod 'approov-service-nsurlsession', '3.5.3'
end
```

Then install the dependency:

```bash
pod install
```

After installation, open the generated `.xcworkspace` file in Xcode rather than the original `.xcodeproj`.

## Initialize Approov

Import the service header:

```objc
#import "ApproovNSURLSession.h"
```

Initialize `ApproovService` once before making requests through `ApproovNSURLSession`. A common place to do this is during app startup.

```objc
NSError *error = nil;

[ApproovService initialize:@"<enter-your-config-string-here>" error:&error];

if (error != nil) {
    NSLog(@"Approov initialization failed: %@", error.localizedDescription);
    // Handle initialization failure before making protected API calls.
}
```

Replace `<enter-your-config-string-here>` with the configuration string provided in your Approov onboarding email or generated by the Approov CLI.

## Use ApproovNSURLSession

Create sessions using `ApproovNSURLSession` instead of `NSURLSession`.

Before:

```objc
NSURLSession *session = [NSURLSession sessionWithConfiguration:NSURLSessionConfiguration.defaultSessionConfiguration];
```

After:

```objc
NSURLSession *session = [ApproovNSURLSession sessionWithConfiguration:NSURLSessionConfiguration.defaultSessionConfiguration];
```

You can then create data, upload, and download tasks in the usual way:

```objc
NSURL *url = [NSURL URLWithString:@"https://api.example.com/v1/example"];
NSURLRequest *request = [NSURLRequest requestWithURL:url];

NSURLSessionDataTask *task = [session dataTaskWithRequest:request
                                        completionHandler:^(NSData *data, NSURLResponse *response, NSError *error) {
    if (error != nil) {
        NSLog(@"Request failed: %@", error.localizedDescription);
        return;
    }

    // Handle the response.
}];

[task resume];
```

For many apps, the simplest migration is to replace `NSURLSession` session creation with `ApproovNSURLSession` session creation for the API calls you want Approov to protect.

## Configure protected API domains

Initially, your app may contact Approov but no API tokens will be added because no API domains have been configured yet. In this state you may see Approov logging such as `UNKNOWN_URL`.

To protect an API domain, add it to Approov using the Approov CLI:

```bash
approov api -add api.example.com
```

After the domain has been added, requests made through `ApproovNSURLSession` to that domain will receive an Approov token in the `Approov-Token` header by default.

Your backend API must verify this token before allowing the request.

## Add your app signing certificate

Approov needs to recognize valid versions of your app. For development and testing, add the Apple signing certificate used to sign your app:

```bash
approov appsigncert -add development.cer -autoReg
```

Apps built for the iOS simulator are not code signed in the same way, so automatic registration through signing certificates does not apply to simulator builds.

## Check that the integration is working

After running your app with Approov initialized, check the live metrics for your Approov account. You should see activity from the app shortly after it starts making requests.

A useful first test is:

1. initialize `ApproovService`;
2. create an `ApproovNSURLSession`;
3. make a request to an API domain;
4. confirm Approov activity appears in live metrics;
5. add the API domain using the Approov CLI;
6. confirm requests to that domain include an `Approov-Token`;
7. verify your backend rejects requests with missing or invalid Approov tokens.

## API protection

Use API protection when you control the backend API and can modify it to verify Approov tokens.

Add the API domain:

```bash
approov api -add api.example.com
```

The service layer will add the token to requests made through `ApproovNSURLSession`:

```http
Approov-Token: <token>
```

By default, the token is sent in the `Approov-Token` header. If your backend expects the token somewhere else, you can change the header name and add a prefix:

```objc
[ApproovService setApproovTokenHeader:@"Authorization"];
[ApproovService setApproovTokenPrefix:@"Bearer "];
```

This sends the Approov token as:

```http
Authorization: Bearer <token>
```

## Token binding

If you want to bind Approov tokens to another request value, such as an OAuth access token or session identifier, set a binding header:

```objc
[ApproovService setBindingHeader:@"Authorization"];
```

When that header is present on a request, the service layer hashes the header value locally and includes the hash in the Approov token. Your backend can then verify that the Approov token is bound to the expected request data.

## Secrets protection

Use secrets protection when your app contains API keys or other secrets that should not be shipped inside the app binary.

First, add the domain where the secret will be sent. If the domain does not need Approov token protection, add it with `-noApproovToken`:

```bash
approov api -add api.example.com -noApproovToken
```

Then add the secret value to Approov:

```bash
approov secstrings -addKey your-secret-name -predefinedValue your-secret-value
```

In your app, replace the real secret with the placeholder name:

```objc
[request setValue:@"your-secret-name" forHTTPHeaderField:@"X-API-Key"];
```

Then tell `ApproovService` which header should be substituted:

```objc
[ApproovService addSubstitutionHeader:@"X-API-Key" requiredPrefix:nil];
```

When a valid app makes the request through `ApproovNSURLSession`, the service layer replaces `your-secret-name` with the real secret value at runtime.

For query parameter substitution:

```objc
[ApproovService addSubstitutionQueryParam:@"api_key"];
```

A URL like this:

```text
https://api.example.com/data?api_key=your-secret-name
```

is transformed at runtime into a request containing the protected value, provided the app passes attestation.

## Fetching a secure string explicitly

Where automatic header or query parameter substitution is not possible, you can fetch a secure string directly:

```objc
NSError *error = nil;
NSString *secret = [ApproovService fetchSecureString:@"your-secret-name" newDef:nil error:&error];

if (error != nil) {
    NSString *type = error.userInfo[@"type"];

    if ([type isEqualToString:@"network"]) {
        // Temporary network issue. Offer the user a retry.
    } else if ([type isEqualToString:@"rejection"]) {
        // App attestation was rejected.
        NSString *arc = error.userInfo[@"rejectionARC"];
        NSString *reasons = error.userInfo[@"rejectionReasons"];
        NSLog(@"Approov rejection. ARC: %@ Reasons: %@", arc, reasons);
    } else {
        // More permanent error.
        NSLog(@"Approov error: %@", error.userInfo[@"message"]);
    }
} else {
    // Use the secret as required.
    // Do not cache, persist, or log the secret value.
}
```

This call may require network access and should not be called from the main UI thread.

## Error handling

Some `ApproovService` methods populate an `NSError` when a problem occurs. The `userInfo` dictionary may include:

* `message`: a descriptive error message;
* `type`: one of `general`, `network`, or `rejection`;
* `rejectionARC`: the Attestation Response Code for a rejection;
* `rejectionReasons`: optional rejection details if enabled for the account.

Handle `network` errors as potentially temporary and allow a retry. Handle `rejection` errors as app attestation failures.

## Proceeding on network failure

By default, if Approov cannot obtain a token because of a network-related problem, the request is not allowed to continue.

You can change this behavior:

```objc
[ApproovService setProceedOnNetworkFailure:YES];
```

Use this with caution. If enabled, your backend may receive requests without the expected Approov token, and the app may connect before dynamic pins have been obtained.

## Excluding URLs

You can exclude matching URLs from Approov processing:

```objc
[ApproovService addExclusionURLRegex:@"https://api.example.com/public/.*"];
```

Use exclusions carefully. If the excluded URL is on a domain that also uses Approov dynamic pinning, make sure your app still has a path to fetch updated Approov configuration and pins.

## Delegates

`ApproovNSURLSession` supports session-level delegates in a similar way to `NSURLSession`.

However, task-specific authentication delegate callbacks are not supported because the service layer already implements a session delegate internally.

If you currently rely on a task-level callback such as:

```objc
- (void)URLSession:(NSURLSession *)session
              task:(NSURLSessionTask *)task
didReceiveChallenge:(NSURLAuthenticationChallenge *)challenge
 completionHandler:(void (^)(NSURLSessionAuthChallengeDisposition disposition,
                              NSURLCredential *credential))completionHandler;
```

move this logic to the session-level delegate form instead:

```objc
- (void)URLSession:(NSURLSession *)session
didReceiveChallenge:(NSURLAuthenticationChallenge *)challenge
 completionHandler:(void (^)(NSURLSessionAuthChallengeDisposition disposition,
                              NSURLCredential *credential))completionHandler;
```
