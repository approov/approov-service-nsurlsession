# Test Plan: Approov NSURLSession Service Layer

This plan maps the NSURLSession service layer to the shared service-layer testing requirements in `/Users/charlesoj/Developer/Test/core-service-layers-testing/TESTING_REQUIREMENTS.md`.

## Scope

The service layer under test is the Objective-C `ApproovService` and `ApproovNSURLSession` implementation, plus the Swift `ApproovServiceMutatorBridge` and message-signing utilities.

Relevant source areas:

- `ApproovService.h` and `ApproovService.m`
- `ApproovNSURLSession.h` and `ApproovNSURLSession.m`
- `ApproovPinningURLSessionDelegate.h` and `ApproovPinningURLSessionDelegate.m`
- `ApproovURLSession/*.swift`
- `ApproovServiceMutatorBridge.swift`
- `tests/ios/native/*`
- `tests/ios/swift/*`

Out of scope for this repository:

- Service-layer-specific APIs from other platforms such as React Native `fetchWithApproov` or Retrofit wrappers.
- Full Approov cloud policy verification in stub-only tests. Those cases are covered by the real SDK integration phase.

## Test Strategy

Use four layers of testing.

1. Stubbed native contract tests

   Extend `tests/ios/native/ApproovNativeTests.m` and `tests/ios/native/TestSupport/Approov/*` to drive `ApproovService` directly with deterministic SDK responses. These tests should run locally without an Approov account, network, simulator, or TLS server.

2. Stubbed Swift message-signing and mutator tests

   Extend `tests/ios/swift/ApproovMessageSigningTests.swift` and the Swift stubs to validate request mutation, HTTP message signatures, body digest policy, and mutator decisions.

3. Mini-SDK contract tests

   Use `tests/ios/minisdk/ApproovMiniSDKContractTests.m` with the shared mini-SDK in `/Users/charlesoj/Developer/Test/core-service-layers-testing/mini-sdk/ios`. These tests exercise the documented service-layer contract with deterministic SDK behavior while still using the shared mini-SDK response model, JWT generation, secure strings, custom JWTs, initialization directives, and pin/config metadata.

4. Simulator integration tests with real SDK and backend fixtures

   Use the lightweight XCTest package generated by `tests/ios/integration/build_integration_package.sh`. It copies the service layer and bundled `Approov.xcframework` into a temporary SwiftPM package and runs iOS simulator tests against a real Approov account, backend echo service, and TLS pinning fixtures. These tests validate behavior that cannot be proven with stubs, including native SDK initialization outcomes, final wire request replay, and certificate pinning.

5. Documentation and API audit

   Use `tests/ios/run_docs_audit.sh` to verify that `REFERENCE.md`, `USAGE.md`, `ApproovService.h`, and `ApproovServiceMutatorBridge.swift` continue to expose and document the common service-layer lifecycle, token/header configuration, binding, exclusions, substitutions, attestation APIs, secure strings, custom JWTs, message signing, mutator behavior, pinning behavior, disabled-mode guards, and deprecated API guidance.

## Added Verification Layers

The mini-SDK closes the deterministic service-layer contract cases. The following verification layers are now added on top of the local green contract suite. Backend replay and real pinning require an Approov test account, simulator, and configured worker URLs before they can be counted as passing evidence.

| --- | --- | --- |
| Documentation artifacts | `REFERENCE.md` and `USAGE.md` are required by the shared requirements. | `tests/ios/run_docs_audit.sh` verifies required API and documentation coverage. |
| Backend replay | Local tests inspect mutated `NSURLRequest` values directly. | `tests/ios/run_backend_replay_tests.sh` runs real SDK iOS simulator XCTest against echo workers and verifies final wire token, trace, method, body, protected, unprotected, and pinning-only behavior. |

## Backend and Fixture Requirements

Stubbed tests should be self-contained. Integration tests need these fixtures:

- Approov test config strings for valid config, alternate config, and failure/rejection scenarios.
- A development key for simulator/device integration tests.
- Protected echo endpoint that returns received method, URL, headers, and body hash.
- Unprotected echo endpoint hosted on a distinct domain or policy path.
- Secure string definitions for valid, empty, one-character, multi-character, and long substitution values.
- Custom JWT test policy that echoes or allows inspection of custom claims.
- HTTPS servers with known valid and invalid SPKI pins.
- A MITM/proxy fixture or controlled SDK stub status for `MITM_DETECTED`, `NO_NETWORK`, and `POOR_NETWORK`.

The backend replay runner requires:

- `APPROOV_CONFIG`
- `APPROOV_DEV_KEY` when the simulator account requires a development key
- `TESTING_REPLY_URL`
- `TESTING_REPLY_URL_UNPROTECTED`
- `TESTING_REPLY_URL_PINNING_ONLY`

The pinning integration runner requires:

- `APPROOV_CONFIG`
- `APPROOV_DEV_KEY` when the simulator account requires a development key
- `TESTING_REPLY_URL`
- `TESTING_REPLY_URL_PINNING_ONLY`

Optional pinning scenarios are enabled with:

- `TESTING_REPLY_URL_INVALID_PIN`
- `TESTING_REPLY_URL_ACCEPT_ANY`
- `TESTING_REPLY_URL_DYNAMIC_PIN_UPDATE`
- `APPROOV_DYNAMIC_PIN_UPDATE_EXPECTED=success|failure`

Both integration runners support `ALLOW_INTEGRATION_SKIPS=1` so CI can validate runner wiring without claiming real backend or pinning evidence when credentials are intentionally unavailable.

- All stubbed native and Swift tests pass on a clean checkout.
- The mini-SDK contract suite passes on a clean checkout.
- The documentation/API audit passes.
- Backend replay integration passes with the documented Approov test account and worker URLs.

- API audit confirms the common interface is exposed or documented as intentionally unsupported.
- Documentation includes the required initialization, disabled-mode, precheck, binding, mutator, message-signing, and deprecated API guidance.
- Known contract gaps are either implemented and covered by passing tests, or explicitly documented as unsupported with an approved exception.
